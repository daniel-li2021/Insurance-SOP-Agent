# ClaimFlow V1 independent reliability, security, and workflow review

Reviewed October 16, 2026 against the V1 checkout beginning at `a107535`, followed by focused corrections. Scope: one local/single-instance synthetic demo, its browser UI, persistent API, and isolated Evaluation Lab. Architecture, dependencies, Agent Playground, top navigation, and Lab layout are preserved. This is a source review with reproduced regressions, not an external penetration test or a production certification.

## Findings and disposition

### Blockers — fixed for the synthetic demo

1. **Partial identity feedback was a guessing oracle.** `identity.verify` returned the best partial match; the public view, `IDENTITY_EVALUATED` event, and “provide N more” response exposed it before verification. Holding other inputs fixed allowed a caller to learn whether a guess improved a stored match. Failed verification now returns no matched fields; the API and inspector expose no partial progress, and chat feedback does not depend on matching stored values. The regression compares feedback for a real and invented name. Existing identity events are sanitized when rendered.

   Rate limits did **not** adequately mitigate the disclosure: six identity-bearing turns were allowed per session, and creating a new session renewed that allowance. The durable client bucket (30 turns/10 minutes) and session-creation bucket (12/hour) slow guesses but survive only for the same transport address, have fixed-window boundaries, and do not prevent distributed attempts. Resetting the UI does not clear those client limits; spoofed forwarded-IP headers do not bypass them. Removing partial feedback is the correction; throttling remains a supplementary demo control. This follows the [OWASP guidance on generic authentication feedback and throttling](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

2. **Fixture-dependent redaction was a second lookup oracle.** Without successful extraction, a stored name/last-four value was replaced while an unknown value remained visible. Redaction now uses supplied extraction and generic credential patterns, never fixture membership. Added fallback handling for labeled names, spelled-out dates, national IDs, full SSNs, and policy numbers. Unknown/unlabeled values can still escape this deliberately limited redactor; it is not a general PII detector. The UI must continue telling reviewers to use synthetic data only.

3. **A policyholder-subject identity could be treated as caller identity.** A mocked interpretation with policyholder-subject fields but `representative=False`, together with “my wife,” previously verified the caller using someone else's details. Supported policyholder-subject evidence now forces the representative restriction, and the deterministic role check covers common family relationships. Three matching policyholder fields never install a representative grant. Unrecognized language still depends on correct subject extraction; this is a reason for targeted live checks, not a claim of complete natural-language identity assurance.

4. **Audit references could cross identity boundaries.** After expiry and verification as another fixture person, the old claim references reappeared because the view showed all referenced events to any verified identity. Events now record their owning party internally; the public view shows referenced events only to that party. Older events without ownership remain stored and their references are hidden. The internal owner is excluded from Playground event JSON. No audit deletion or database migration is needed.

5. **Browser expiry depended on a successful refresh.** The server correctly rejected expired access, but a failed network refresh left protected text and summaries on screen after the visible authorization deadline. A reproduced Playwright failure showed the stale summary still present. The browser now hides protected content immediately at the deadline and on HTTP 401. Backend authorization remains authoritative; browser state cannot grant access. Local hiding cannot erase information already read, copied, or captured by a caller.

### Should-fix — corrected in this review

6. **A simulated-sent summary remained current-looking after follow-ups and case switches.** All new conversation now clears the summary card, including sent previews. The historical send event/message remains; its old receipt is no longer displayed as the current discussion result. A fresh review creates a new ID and requires a new explicit decision. Send retries for the same unchanged preview remain idempotent. Old IDs are rejected after further discussion. The cross-case summary still covers the authorized cases actually discussed.

7. **Authorization expiry retained old claim hints and intent.** An expired Margaret session could carry its denied-January selection into verification as Ava. Expiry now clears hints, intent, unresolved tasks, and the grant along with identity, protected messages, case choices, and discussion memory. A change of identity already invalidates protected history and requires a fresh consistent match.

8. **The view did not invalidate an unusable representative grant.** Repository reads checked scopes, but the session view previously trusted `party_id` plus time. Missing principal proof, wrong party, missing `claims:read`, and expired grants now invalidate authorization before rendering. This is defensive consistency for the evaluator-only grant path; public callers cannot install grants.

9. **The offline parser treated claim dates as DOB changes.** “The appeal deadline was March 18, 2026” extracted a DOB and revoked verified access. Reproduced before fixing. DOB parsing now requires an explicit birth-date label or a short verification/correction answer. Tests retain labeled dates, unlabelled verification dates, and explicit corrections, including a message containing both a claim date and DOB. This does not turn the scripted parser into a general language model.

10. **Lab assertions could pass on old events and counted sends per scenario rather than per preview.** Required event codes are now checked only among events from the current step. Explicit action outcomes and fresh preview IDs are asserted. Send counts are bound to each preview, permitting two legitimate summaries while rejecting duplicate success for either. Locked views are checked for zero partial feedback, protected messages, summaries, case choices, and evidence references. Four new shared scenarios exercise privacy, identity revocation, post-send follow-up, and post-send case switching. The Lab still uses handcrafted interpretations; it does not measure live extraction accuracy.

### Optional / outside the current delivery scope

- Broader conversation-quality measurement is useful before claiming robust natural conversation. Run the bounded suite below; do not add another agent framework or let generated prose control facts or authorization.
- Reviewers may find repeated status/deadline blocks verbose. A later phrasing pass could reduce repetition while rendering the same authorized structured facts. No redesign is required for V1.
- Production identity proof, account-aware anti-abuse controls, approved representative enrollment, retention/backup operations, provider data-handling review, and real action integrations are separate work. They become blockers if the demo is repurposed for real customer data. The supplied static PII threshold is not production authentication.

## End-to-end boundary trace

- **Verification:** HTTP validates ownership cookie, CSRF/origin, input size, request UUID/version, and durable lease. The interpreter supplies bounded candidates; `supported` checks each candidate against this turn's literal evidence and normalization. A dictionary keyed by category prevents repeated aliases from counting twice. Three approved distinct categories must match one unique fixture person, without contradictory fields. Policy numbers restrict matching but never contribute a field. Explicit correction replaces a value; an unexplained change creates a conflict. The model cannot set `party_id`, grants, phases, or stored facts.
- **Early memory:** caller hints, topics, and emotional context are captured before verification; no claim read occurs while locked. A successful verification can advance through ordered phases and answer the retained question. New-case context clears the active selection while retaining a per-case discussion map for the same authorized person. Expiry/reverification clears protected context; audit references stay owner scoped.
- **Representative authorization:** being David, a spouse, or another relative is not authority. Public chat remains blocked without independent representative proof and a scoped grant. Only isolated policy evaluations create mock grants; approved fixture consent sequences alone provide neither principal proof nor email consent. Read scope and policyholder-email scope are distinct; read-only representatives cannot send.
- **Case resolution and processing:** every claim read passes `Fixtures.authorize` and filters by party. Ambiguous January claims prompt a selection; another customer's case cannot be read. Facts, money (`Decimal`), document guidance, and the expired March 18 deadline come from the fixtures. No document receipt, appeal acceptance, payout, upload, or human transfer is fabricated. Emotion selects bounded empathy; the model does not write factual answers or execute tools.
- **Follow-up and consent:** previews are server-created snapshots with a new UUID, on-file masked recipient, and 10-minute offer. Chat “yes” is not Send. Only the CSRF-protected explicit action can simulate Send/Skip. Failed/time-out simulation branches permit explicit retry before expiry. A committed success deduplicates; expired, skipped, replaced, or conversation-invalidated previews cannot be sent. Simulated Send never contacts email infrastructure.
- **Session lifetime and persistence:** authorization expires 15 minutes after the most recent authorized chat turn; server session retention is 24 hours since the last committed mutation, while the browser cookie also has a 24-hour lifetime. Summary actions do not extend authorization. Fernet encrypts payloads; the generated private key must persist with the SQLite volume. Request fingerprints use HMAC, and durable leases/version checks prevent stale work from overwriting a newer turn. Expired duplicate requests return a newly filtered current view, not the original protected response. GET expiry filtering is lazy and not committed until a mutation; every subsequent access rechecks the clock.
- **API/data exposure:** no client request can supply a grant, replacement summary body, alternate recipient, or claim mutation. Model failures do not persist the failed raw turn or advance state; uncertain calls retain their token reservation. CSRF, same-site cookies, origin checks, CSP, request limits, and a daily token budget are demo defenses. Encryption is not separation from an administrator who can read both the key and database. The model receives the current raw message and bounded conversational context; `store=False` is not a complete provider retention agreement.

The guided-starter endpoint intentionally exposes a fictional identity. The public Lab intentionally returns synthetic claim examples through isolated evaluations without verifying the Playground customer. The repository also ships these fixtures. These are reviewer affordances, so the demo's authentication boundary must not be described as confidentiality for the supplied dataset. Use new, genuinely authenticated services if real records are ever introduced.

## Proposed targeted live acceptance suite — not executed

Twelve calls, five short conversations, synthetic fixtures only. Use the existing model/prompt configuration and a fixed controller clock; save sanitized outcomes and latency/token usage. Obtain approval for the paid run before execution.

1. **Corrections and date roles (3 calls):** start with two correct fields plus an incorrect DOB and an early denial question; explicitly correct the DOB with a short answer; then discuss the appeal deadline date. Assert no reads before full verification, the retained question is answered after verification, and the claim date cannot revoke or change identity.
2. **Refusal and alternate fields (3 calls):** supply one field and an early document question; express frustration/refusal to give SSN; offer phone and email instead. Assert empathy without partial-match hints, no early disclosure, and reuse of the document question after three valid categories.
3. **Representative ambiguity and injection (2 calls):** discuss a spouse's supplied details using pronouns and an instruction to assume a grant; then claim to be the policyholder. Assert sticky representative restriction, no read/send, and a clear member-support route without promising a transfer.
4. **Case switching after Send (2 calls):** verify and discuss the 2026 denial; use deterministic preview/Send actions between calls, then ask about “last year's closed January medical claim” without an ID. Assert CL-2011 selection, disappearance of the prior summary, correct payment/status, and a new consent requirement.
5. **Contextual follow-up (2 calls):** verify and ask about obtaining missing records; ask “what if neither of those is obtainable?” Assert correct alternative-document topics, conditional guidance, an appropriate human-review offer, and no invented acceptance or receipt.

Keep deterministic security assertions separate from a short human reading of clarity, empathy, relevance, and repetition. One pass is acceptance evidence, not a statistical reliability estimate. Clock expiry, duplicate actions, rate limits, and network failure are already better tested deterministically; they need no paid calls.

## Readiness

The scoped V1 can be presented as a synthetic SOP harness with deterministic facts/actions, limited scripted mode, and historical live interpretation evidence. There are no remaining reproduced blockers in that scope after the corrections and checks above. Natural language interpretation is plausible for the assignment's guided journey, but broad messy-language quality remains unverified; do not claim that it is universally natural or safe. A real-customer service, independent penetration-test claim, production healthcare claim, or claim of real email/action delivery is not ready.
